# Decisions

1. **Three repos kept in sync** (replaces "mobile-only changes", 29 Oct 2026). The app leads; a feature is done when the API serves it, the app uses it with its mock off, and the website has the same screens. The API's OpenAPI spec is the one contract. See `Architecture/09-sync-plan.md` in the workspace.
2. **Docs live in `docs/mobile/`** inside this repo so they version with the code.
3. **Plus Jakarta Sans** chosen as the closest free match to District's geometric sans.
4. **Single phone entry for login + signup** (Welcome): `POST /v1/account/otp` with purpose `signup` answering `PHONE_TAKEN` → routes to Login.
5. **SMS-only OTP resend** — backend has no WhatsApp channel.
6. **No "Skip" / guest mode** — District has it; Ruxstar requires an account for every role.
7. **Hero plays `assets/animations/online-shopping.json`** (Lottie, 5 s, one pass, no loop; recoloured to the District-style purple palette) under the Ruxstar wordmark, with a `HeroCaption` that steps through Feed / Print / Events / Stay / Learn once. Reduced motion shows its final frame. It fades and shrinks away as the keyboard opens (`useKeyboardProgress`), matching the District welcome transition.
8. **Sentry for crash reporting** (`@sentry/react-native`), PII off, sensitive keys scrubbed.
9. **Jest (jest-expo)** for pure-logic tests. `@react-native/jest-preset` is pinned to the same
   version as `react-native` — keep them in lockstep when upgrading.
10. **Forgot password is real:** code with purpose `reset`, then `POST /v1/account/password/reset`, which signs out every device. (Was mocked until 29 Oct 2026.)
11. **tsconfig `types: ["jest", "node"]`** — required because TypeScript no longer auto-includes `@types/*`.
12. **Mock any endpoint the backend lacks** (`src/services/mock`, flag `mocked`, env `EXPO_PUBLIC_USE_MOCKS`). Every call is listed in `API_CONTRACTS.md`. The backend team owns the real routes.
13. **Scope = 13 Oct 2026 review.** No creator, general-commerce or restaurant UI; admin web-only until 11 Nov 2026 (see 29); delivery lives in this app (no separate delivery app, 29 Oct 2026). Hero captions are Feed · Print · Events · Stay · Learn.
14. **Theme default (until the user changes it):** purple on near-black, white primary pill button, District-style. Tokens are finalised in Phase 1 and then frozen (changes need user approval).
15. **Tracking system:** `AGENTS.md` (rules), `LOG.md` (work log), `DECISIONS.md`, `API_CONTRACTS.md`, `DELIVERABLES.md`, runtime `createLogger` with redaction.
16. **Signup is one call:** name, date of birth (13+), gender, optional email, username, password and `acceptTerms` all go to `POST /v1/account/signup`, then a one-time success screen (`(customer)/welcome`). The photo step waits for file uploads.
17. **Login uses Password / One-time code tabs** (prototype behaviour); the shaking "Forgot?" link replaces the old "OTP instead" nudge.
18. **Profile data split:** name/phone live in the auth store (from login); everything else comes from `GET /v1/account/me`. Posts, engagements and rating read as zero until the social module ships. Screens load through `useAsyncResource` + `AsyncBoundary`; toggles and removals are optimistic with rollback.
19. **KYC is data-driven:** flows are declarative step lists run by one hook/screen. Vendor and delivery add-ons unlock only after base KYC is verified. Raw ID numbers and photos are never persisted on device or logged.
20. **Lists:** `usePaginated` (cursor, one request in flight) for feed/comments/notifications; `FlatList` only, never `map` in a `ScrollView`; likes/saves are optimistic. Post sheets live in `usePostMenu`, not per screen.
21. **Chat transport is polling** behind `useThread` (3 s focused, 15 s for the list and the tab badge). Swap in sockets/push by changing that hook and `use-messages-unread` only.
22. **Roles stack:** `useAuthStore.roles` authorises access, built from the API's `roles { vendor, delivery, ruxstarStaff, admin }` (the old `customer` / `employee` strings are gone). Every account lands in the user app; the vendor portal (`(vendor)`) and the delivery area (`(partner)`) open only with their role, entered from Profile. Admins and Ruxstar staff are the exception: they land in `(admin)` and get nothing else (29). CLAUDE.md §6's role→home table is superseded.
23. **One checkout for every module:** `PaymentSheet` (review → method → pay → retry) and `usePaidAction` (pay, then create with the payment reference; a failed create keeps the reference so retry never charges twice). Backend create endpoints must be idempotent on `paymentRef`. Prepaid only, no COD.
24. **Pricing/availability rules live in pure, tested code** (`features/pod/lib/pricing.ts`, `features/stays/lib/availability.ts`, `features/coaching/lib/policy.ts`) and mirror what the server must enforce; the server stays authoritative.
25. **One ledger:** every paid purchase writes a ledger line from its payment reference (`commerce-state.ts` in the mock; the real ledger is the backend's). Vendor net = item total − module commission − vendor-funded discount; delivery fee is never the vendor's. Coupons are validated server-side; prices shown in the app are previews.
26. **Delivery partner is self-contained:** `features/delivery`, `services/delivery-service.ts`, `(partner)` group; nothing else in the app imports from it except the Profile entry. It stays in this app; there is no separate delivery app.
27. **API client (29 Oct 2026):** every call sends `X-Client: app` and `X-App-Version` (from `app.json`), unwraps `{ data }`, and turns `{ error: { code, message, details } }` into `ApiError` with `code`, `details` and `retryAfterSeconds`. Screens branch on `code`, never on text. Lock waits come from `retryAfterSeconds`.
28. **Sessions:** access token (15 min) and refresh token (30 days, single use) live in the secure store (Keychain/Keystore; AsyncStorage only on web). On `UNAUTHENTICATED` the client refreshes once, shared by parallel calls, and retries; a refused refresh signs out.
29. **Ruxstar console in the app (11 Nov 2026, Architecture decision 42):** admins and active Ruxstar staff see only `(admin)`: Dashboard, Verification, Reports and People tabs, and More (Staff for admins, Modules, Audit log, Change password, Sessions, Log out). `AuthGuard` sends them there and keeps them out of `(customer)`, `(vendor)` and `(partner)`; everyone else is sent out of `(admin)`. `features/admin/access.tsx` loads `GET /v1/ruxstar/access` once and hides what it does not allow; the API still checks every route. Writes pass an `Idempotency-Key` from `newIdempotencyKey()`, kept until the action succeeds.
30. **Vendor portal, phase 1 (11 Nov 2026, Architecture decision 43):** identity approval makes you a vendor; there is no vendor verification step. The Profile storefront button is grey (opens Verification) until `badges` includes `vendor`, then white like the primary button, `Brand.action` (opens `/(vendor)/dashboard`); `ProfileScreen` and `VerificationScreen` call `addRole(ROLES.VENDOR)` so no new sign-in is needed. `/(vendor)/dashboard` is `VendorHomeScreen` on the real API (`services/business-service.ts`): businesses list, Add a business (`businesses/new`), each business (`businesses/[id]`, photos, publish, open/closed, delete draft) and its details (`businesses/[id]/details`), and Payments (`payments`: balance, bank or UPI payout method, payouts). Amounts arrive in paise. The mock vendor routes (team, audit, orders, earnings, coupons, events, coaching, stays) are deleted; the module screens they opened stay in the tree, unreachable, until their module phases replace them. The console adds Businesses under More (`businesses.view`, hold and restore with `businesses.manage`); business hold notifications open that business.
31. **Navigation and surfaces (12 Nov 2026):** the root layout is a `Stack`, so the vendor portal and partner area open on top of Profile and Back returns there; every tab group uses `backBehavior="history"`. `useRefetchOnFocus` keeps the latest callback in a ref, so an inline callback cannot loop. Entry animations are timed fades, no springs. Cards and panels are `Brand.surface` (#1A1922) with a 1px `Brand.border` outline; the website uses the same values (`--surface`, `--raised`, `--line`). Profile shows role badges only (no "Normal user"). Once verified, the Ruxstar Card stands on the page without the Identity panel behind it, and the website card is matte black with champagne like the app's.
32. **Adding a business and print on demand setup (12 Nov 2026, Architecture decision 44):** `businesses/new` is one screen in three steps, category then type then profile; a category with one type skips the type step. `useBusinessCatalog` reads `GET /v1/vendor/catalog` once per session (Add a business re-reads it for module state). `BusinessProfileFields` is shared by Add a business and Edit details: name, phone, "Use current location" (expo-location's own reverse geocoder, matched to the catalog's states and cities), State and City selects (`components/ui/SelectField`, searchable, with "Other" for a typed city), door number, building, street, area, PIN code and a 500-character description. A print on demand business shows two setup steps on its page: Products & delivery (`businesses/[id]/products`) and Prices (`businesses/[id]/prices`, one screen per product at `prices/[product]`). Rupee fields take up to two decimals and are sent as paise (`features/vendor/lib/pod.ts`).
33. **Vendor portal tabs (12 Nov 2026):** the portal is `(vendor)/(tabs)` with Dashboard, Businesses, Orders, Posts and Payments, replacing `VendorHomeScreen`; every tab has "Vendor portal" and Exit (`router.dismissTo` Profile) above its title. The tab files are `dashboard`, `shops`, `sales`, `posts` and `payments`, so their URLs never clash with the console's `/businesses` or the customer's `/orders`. Dashboard shows open, closed and draft counts, what drafts still need, and the balance; it has no open-all switch. Businesses has an Open switch on each business that can open (live, not on hold, module not paused); a business page has Open | Closed at the top. Switches flip at once and revert on failure. Orders is empty until a module takes orders. Posts lists the vendor's business posts with Post as business.
34. **Discover (12 Nov 2026, Architecture decision 45):** the Discover tab lists real print shops from `GET /v1/pod/shops` (`services/shop-service.ts`), with a search box, a first row of category chips (All and the catalog's four categories; one that is not live, or has no Discover yet, shows "coming soon") and, under Print on demand, a second row of smaller outlined chips per print product; the mock listings and `CommerceService.discover` are gone. Each `ShopCardView` is a 16:9 cover (the smallest copy wide enough for the screen, or an initial on colours from the name) with an Open or Closed pill, then name, price from, type and place, ready time and delivery. `pod/shop/[id]` is now `ShopScreen`: swipeable photos, facts, About, What they print, From the shop, and a fixed bar with the price and Order. Order shows a note until ordering ships; the mock `PodOrderScreen` stays unreachable until then. The website has the same at `/discover` and `/b/{id}`.
35. **Print ordering (12 Nov 2026, Architecture decision 46):** Order on a shop opens `pod/new/[shopId]` (`PlaceOrderScreen`): product, option chips, B&W or colour for documents, quantity, files from the document picker (uploaded at once as raw bytes with `apiPostBytes`), an address filled from the last order or the account, a note, and a quote from `POST /v1/pod/quote` re-asked 350 ms after each change. Pay places the order with an `Idempotency-Key` and replaces the screen with `pod/order/[id]?pay=1`, which opens the API's checkout page with `WebBrowser.openAuthSessionAsync` back to `pod/paid`, a screen that only closes itself. The order screen re-reads the order every 8 seconds until it is finished; the API, never the app, decides it is paid. Orders (`/(customer)/orders`) lists real print orders. The vendor Orders tab has New, In progress and Past, and `(vendor)/sale/[id]` (`ShopOrderScreen`) shows what to print, the files (10-minute links opened in the browser), the address with a call link, the money with commission and payout, and the next steps from `nextSteps`; Turn down asks for a reason. Order notifications open these screens. Modules in the console has a platform fee in rupees next to the commission. `services/order-service.ts` and `types/order.ts` hold the client; the mock `pod.mocks.ts` stays only for the old money and delivery mock tests.
36. **Follows, feed tabs, blocks and business posts (12 Nov 2026, Architecture decision 47):** the feed has For you (the API ranks the last week by likes and comments, people you follow boosted) and Following (people you follow and you, newest first); switching tabs reloads the list. Follows are open, no requests. Profiles show Posts, Followers and Following, where Engagements and the empty Rating used to be; the two counts open `people/[id]` (`FollowListScreen`, Followers | Following, Follow on each person). Someone else's profile has Follow (Follow back when they follow you), Message and a menu with Block and Report; a block hides both people from each other and ends follows both ways, and the profile then shows Unblock instead of posts. Reporting a person uses its own reasons (`USER_REPORT_REASONS`); `ReportSheet` takes the list. Settings has Blocked accounts on `GET /v1/social/blocks`; the mocked block, unblock and report calls are gone. A business post shows its business with Order (`pod/new/[shopId]`) when it is a live print shop taking orders; Post as business asks which business when the vendor has more than one. Follow notifications open the follower's profile. The console Reports tab has Posts | People; People reports are dismissed there, or closed by putting the account on hold.
37. **Chats (12 Nov 2026, Architecture decision 49):** the mock chats are gone; `services/chat-service.ts` calls `/v1/social/chats`. Messages has Chats | Requests (with a count); the tab badge is unread plus requests. Anyone can start a 1:1 chat, from a profile's Message or New chat; a chat from someone you don't follow lands in Requests, and the sender can't send again until it is accepted (`CHAT_REQUEST_PENDING`, shown above the composer). Replying accepts. Groups hold up to 50 people; their creator is admin, admins rename, add, remove and make admins, and anyone can leave; being added by someone you don't follow is a request too. Messages are text, a shared post (the post's Share opens `SharePostSheet`: recent chats or a people search, then Share link for other apps) or a photo (resized to 1280 px JPEG, shown from a one-hour signed link). Long-press your own message to unsend it for everyone. Seen shows under your last message a 1:1 peer has read. Chat info (`chat/info/[id]`) has Mute, the people list and the admin actions. Sends are optimistic with an `Idempotency-Key` per message, and a failed one keeps its key for Retry. There is no message reporting.
