# Decisions

1. **Three repos kept in sync** (replaces "mobile-only changes", 29 Oct 2026). The app leads; a feature is done when the API serves it, the app uses it with its mock off, and the website has the same screens. The API's OpenAPI spec is the one contract. See `Architecture/09-sync-plan.md` in the workspace.
2. **Docs live in `docs/mobile/`** inside this repo so they version with the code.
3. **Plus Jakarta Sans** chosen as the closest free match to District's geometric sans.
4. **Single phone entry for login + signup** (Welcome): `POST /v1/account/otp` with purpose `signup` answering `PHONE_TAKEN` → routes to Login.
5. **SMS-only OTP resend** — backend has no WhatsApp channel.
6. **No "Skip" / guest mode** — District has it; Ruxstar requires an account for every role.
7. **Hero plays `assets/animations/online-shopping.json`** (Lottie, 5 s, one pass, no loop; recoloured to the District-style purple palette) under the Ruxstar wordmark, with a `HeroCaption` that steps through Feed / Print / Events / Stay / Learn once. Reduced motion shows its final frame. It fades and shrinks away as the keyboard opens (`useKeyboardProgress`), matching the District welcome transition.
8. **Sentry for crash reporting** (`@sentry/react-native`), PII off, sensitive keys scrubbed.
9. **Jest (jest-expo)** for pure-logic tests. `@react-native/jest-preset` is pinned to the same
   version as `react-native` — keep them in lockstep when upgrading.
10. **Forgot password is real:** code with purpose `reset`, then `POST /v1/account/password/reset`, which signs out every device. (Was mocked until 29 Oct 2026.)
11. **tsconfig `types: ["jest", "node"]`** — required because TypeScript no longer auto-includes `@types/*`.
12. **Mock any endpoint the backend lacks** (`src/services/mock`, flag `mocked`, env `EXPO_PUBLIC_USE_MOCKS`). Every call is listed in `API_CONTRACTS.md`. The backend team owns the real routes.
13. **Scope = 13 Oct 2026 review.** No creator, general-commerce or restaurant UI; admin web-only until 11 Nov 2026 (see 29); riders use the separate Ruxstar Delivery app (45; replaces "delivery lives in this app", 29 Oct 2026). Hero captions are Feed · Print · Events · Stay · Learn.
14. **Theme default (until the user changes it):** purple on near-black, white primary pill button, District-style. Tokens are finalised in Phase 1 and then frozen (changes need user approval).
15. **Tracking system:** `AGENTS.md` (rules), `LOG.md` (work log), `DECISIONS.md`, `API_CONTRACTS.md`, `DELIVERABLES.md`, runtime `createLogger` with redaction.
16. **Signup is one call:** name, date of birth (13+), gender, optional email, username, password and `acceptTerms` all go to `POST /v1/account/signup`, then a one-time success screen (`(customer)/welcome`). The photo step waits for file uploads.
17. **Login uses Password / One-time code tabs** (prototype behaviour); the shaking "Forgot?" link replaces the old "OTP instead" nudge.
18. **Profile data split:** name/phone live in the auth store (from login); everything else comes from `GET /v1/account/me`. Posts, engagements and rating read as zero until the social module ships. Screens load through `useAsyncResource` + `AsyncBoundary`; toggles and removals are optimistic with rollback.
19. **KYC is data-driven:** flows are declarative step lists run by one hook/screen. Vendor and delivery add-ons unlock only after base KYC is verified. Raw ID numbers and photos are never persisted on device or logged.
20. **Lists:** `usePaginated` (cursor, one request in flight) for feed/comments/notifications; `FlatList` only, never `map` in a `ScrollView`; likes/saves are optimistic. Post sheets live in `usePostMenu`, not per screen. Changes to a post (likes, saves, comment counts, edits, deletes) go to `feed-store`, and every list shows them through `useLatestPosts` until it next loads from the API.
21. **Chat transport is polling** behind `useThread` (3 s focused, 15 s for the list and the tab badge). Swap in sockets/push by changing that hook and `use-messages-unread` only.
22. **Roles stack:** `useAuthStore.roles` authorises access, built from the API's `roles { vendor, delivery, ruxstarStaff, admin }` (the old `customer` / `employee` strings are gone). Every account lands in the user app; the vendor portal (`(vendor)`) opens only with its role, entered from Profile. The delivery role opens nothing here; riders use the Ruxstar Delivery app (45). Admins and Ruxstar staff are the exception: they land in `(admin)` and get nothing else (29). CLAUDE.md §6's role→home table is superseded.
23. **One checkout for every module:** `PaymentSheet` (review → method → pay → retry) and `usePaidAction` (pay, then create with the payment reference; a failed create keeps the reference so retry never charges twice). Backend create endpoints must be idempotent on `paymentRef`. Prepaid only, no COD.
24. **Pricing/availability rules live in pure, tested code** (`features/pod/lib/pricing.ts`, `features/stays/lib/availability.ts`, `features/coaching/lib/policy.ts`) and mirror what the server must enforce; the server stays authoritative.
25. **One ledger:** every paid purchase writes a ledger line from its payment reference (`commerce-state.ts` in the mock; the real ledger is the backend's). Vendor net = item total − module commission − vendor-funded discount; delivery fee is never the vendor's. Coupons are validated server-side; prices shown in the app are previews.
26. ~~**Delivery partner is self-contained** in this app (`features/delivery`, `(partner)`).~~ Replaced by 45 (14 Nov 2026): the mock partner area is deleted and riders use the Ruxstar Delivery app.
27. **API client (29 Oct 2026):** every call sends `X-Client: app` and `X-App-Version` (from `app.json`), unwraps `{ data }`, and turns `{ error: { code, message, details } }` into `ApiError` with `code`, `details` and `retryAfterSeconds`. Screens branch on `code`, never on text. Lock waits come from `retryAfterSeconds`.
28. **Sessions:** access token (15 min) and refresh token (30 days, single use) live in the secure store (Keychain/Keystore; AsyncStorage only on web). On `UNAUTHENTICATED` the client refreshes once, shared by parallel calls, and retries; a refused refresh signs out.
29. **Ruxstar console in the app (11 Nov 2026, Architecture decision 42):** admins and active Ruxstar staff see only `(admin)`: Dashboard, Verification, Reports and People tabs, and More (Staff for admins, Modules, Audit log, Change password, Sessions, Log out). `AuthGuard` sends them there and keeps them out of `(customer)` and `(vendor)`; everyone else is sent out of `(admin)`. `features/admin/access.tsx` loads `GET /v1/ruxstar/access` once and hides what it does not allow; the API still checks every route. Writes pass an `Idempotency-Key` from `newIdempotencyKey()`, kept until the action succeeds.
30. **Vendor portal, phase 1 (11 Nov 2026, Architecture decision 43):** identity approval makes you a vendor; there is no vendor verification step. The Profile storefront button is grey (opens Verification) until `badges` includes `vendor`, then white like the primary button, `Brand.action` (opens `/(vendor)/dashboard`); `ProfileScreen` and `VerificationScreen` call `addRole(ROLES.VENDOR)` so no new sign-in is needed. `/(vendor)/dashboard` is `VendorHomeScreen` on the real API (`services/business-service.ts`): businesses list, Add a business (`businesses/new`), each business (`businesses/[id]`, photos, publish, open/closed, delete draft) and its details (`businesses/[id]/details`), and Payments (`payments`: balance, bank or UPI payout method, payouts). Amounts arrive in paise. The mock vendor routes (team, audit, orders, earnings, coupons, events, coaching, stays) are deleted; the module screens they opened stay in the tree, unreachable, until their module phases replace them. The console adds Businesses under More (`businesses.view`, hold and restore with `businesses.manage`); business hold notifications open that business.
31. **Navigation and surfaces (12 Nov 2026):** the root layout is a `Stack`, so the vendor portal and partner area open on top of Profile and Back returns there; every tab group uses `backBehavior="history"`. `useRefetchOnFocus` keeps the latest callback in a ref, so an inline callback cannot loop. Entry animations are timed fades, no springs. Cards and panels are `Brand.surface` (#1A1922) with a 1px `Brand.border` outline; the website uses the same values (`--surface`, `--raised`, `--line`). Profile shows role badges only (no "Normal user"). Once verified, the Ruxstar Card stands on the page without the Identity panel behind it, and the website card is matte black with champagne like the app's.
32. **Adding a business and print on demand setup (12 Nov 2026, Architecture decision 44):** `businesses/new` is one screen in three steps, category then type then profile; a category with one type skips the type step. `useBusinessCatalog` reads `GET /v1/vendor/catalog` once per session (Add a business re-reads it for module state). `BusinessProfileFields` is shared by Add a business and Edit details: name, phone, "Use current location" (expo-location's own reverse geocoder, matched to the catalog's states and cities), State and City selects (`components/ui/SelectField`, searchable, with "Other" for a typed city), door number, building, street, area, PIN code and a 500-character description. A print on demand business shows two setup steps on its page: Products & delivery (`businesses/[id]/products`) and Prices (`businesses/[id]/prices`, one screen per product at `prices/[product]`). Rupee fields take up to two decimals and are sent as paise (`features/vendor/lib/pod.ts`).
33. **Vendor portal tabs (12 Nov 2026):** the portal is `(vendor)/(tabs)` with Dashboard, Businesses, Orders, Posts and Payments, replacing `VendorHomeScreen`; every tab has "Vendor portal" and Exit (`router.dismissTo` Profile) above its title. The tab files are `dashboard`, `shops`, `sales`, `posts` and `payments`, so their URLs never clash with the console's `/businesses` or the customer's `/orders`. Dashboard shows open, closed and draft counts, what drafts still need, and the balance; it has no open-all switch. Businesses has an Open switch on each business that can open (live, not on hold, module not paused); a business page has Open | Closed at the top. Switches flip at once and revert on failure. Orders is empty until a module takes orders. Posts lists the vendor's business posts with Post as business.
34. **Discover (12 Nov 2026, Architecture decision 45):** the Discover tab lists real print shops from `GET /v1/pod/shops` (`services/shop-service.ts`), with a search box, a first row of category chips (All and the catalog's four categories; one that is not live, or has no Discover yet, shows "coming soon") and, under Print on demand, a second row of smaller outlined chips per print product; the mock listings and `CommerceService.discover` are gone. Each `ShopCardView` is a 16:9 cover (the smallest copy wide enough for the screen, or an initial on colours from the name) with an Open or Closed pill, then name, price from, type and place, ready time and delivery. `pod/shop/[id]` is now `ShopScreen`: swipeable photos, facts, About, What they print, From the shop, and a fixed bar with the price and Order. Order shows a note until ordering ships; the mock `PodOrderScreen` stays unreachable until then. The website has the same at `/discover` and `/b/{id}`.
35. **Print ordering (12 Nov 2026, Architecture decision 46):** Order on a shop opens `pod/new/[shopId]` (`PlaceOrderScreen`): product, option chips, B&W or colour for documents, quantity, files from the document picker (uploaded at once as raw bytes with `apiPostBytes`), an address filled from the last order or the account, a note, and a quote from `POST /v1/pod/quote` re-asked 350 ms after each change. Pay places the order with an `Idempotency-Key` and replaces the screen with `pod/order/[id]?pay=1`, which opens the API's checkout page with `WebBrowser.openAuthSessionAsync` back to `pod/paid`, a screen that only closes itself. The order screen re-reads the order every 8 seconds until it is finished; the API, never the app, decides it is paid. Orders (`/(customer)/orders`) lists real print orders. The vendor Orders tab has New, In progress and Past, and `(vendor)/sale/[id]` (`ShopOrderScreen`) shows what to print, the files (10-minute links opened in the browser), the address with a call link, the money with commission and payout, and the next steps from `nextSteps`; Turn down asks for a reason. Order notifications open these screens. Modules in the console has a platform fee in rupees next to the commission. `services/order-service.ts` and `types/order.ts` hold the client; the mock `pod.mocks.ts` stays only for the old money and delivery mock tests.
36. **Follows, feed tabs, blocks and business posts (12 Nov 2026, Architecture decision 47):** the feed has For you (the API ranks the last week by likes and comments, people you follow boosted) and Following (people you follow and you, newest first); switching tabs reloads the list. Follows are open, no requests. Profiles show Posts, Followers and Following, where Engagements and the empty Rating used to be; the two counts open `people/[id]` (`FollowListScreen`, Followers | Following, Follow on each person). Someone else's profile has Follow (Follow back when they follow you), Message and a menu with Block and Report; a block hides both people from each other and ends follows both ways, and the profile then shows Unblock instead of posts. Reporting a person uses its own reasons (`USER_REPORT_REASONS`); `ReportSheet` takes the list. Settings has Blocked accounts on `GET /v1/social/blocks`; the mocked block, unblock and report calls are gone. A business post shows its business with Order (`pod/new/[shopId]`) when it is a live print shop taking orders; Post as business asks which business when the vendor has more than one. Follow notifications open the follower's profile. The console Reports tab has Posts | People; People reports are dismissed there, or closed by putting the account on hold.
37. **Chats (12 Nov 2026, Architecture decision 49):** the mock chats are gone; `services/chat-service.ts` calls `/v1/social/chats`. Messages has Chats | Requests (with a count); the tab badge is unread plus requests. Anyone can start a 1:1 chat, from a profile's Message or New chat; a chat from someone you don't follow lands in Requests, and the sender can't send again until it is accepted (`CHAT_REQUEST_PENDING`, shown above the composer). Replying accepts. Groups hold up to 50 people; their creator is admin, admins rename, add, remove and make admins, and anyone can leave; being added by someone you don't follow is a request too. Messages are text, a shared post (the post's Share opens `SharePostSheet`: recent chats or a people search, then Share link for other apps) or a photo (resized to 1280 px JPEG, shown from a one-hour signed link). Long-press your own message to unsend it for everyone. Seen shows under your last message a 1:1 peer has read. Chat info (`chat/info/[id]`) has Mute, the people list and the admin actions. Sends are optimistic with an `Idempotency-Key` per message, and a failed one keeps its key for Retry. There is no message reporting.
38. **Print order rules (12 Nov 2026, Architecture decision 50):** the API owns every clock; the app only shows them. A placed order shows "accept by" (6 hours after payment, then it is cancelled and refunded); an accepted one shows "Ready by" (acceptance plus the shop's ready-in days). The tracking screen lists partial refunds, and from delivery for 48 hours, or any time a late order is still not delivered, offers Report a problem (`ReportSheet`: not received, wrong print, poor quality, damaged or other, and a note), then up to 3 photos added on the `ProblemCard` (picked, resized to 1600 px JPEG, sent as raw bytes with an `Idempotency-Key`, shown from 10-minute links). `refunded` is a status of its own, closed like cancelled. The shop's order screen shows the problem, "Refund part of this order" (rupees up to `refundable`, a reason, out of the shop's share) and when its share becomes available (48 hours after delivery, held while a problem is open). Payments lists Coming up: each order's share with its date, or Held. The console Reports tab has Posts | People | Orders, open to `reports.view` or `orders.view`; Orders settles a problem with Refund in full, Refund part or Close without a refund, each with an answer the customer and the shop see, and needs `orders.manage`. The dashboard counts open order problems.
39. **Vendor withdrawals and the statement (13 Nov 2026, Architecture decision 52):** no weekly payout run. Each module has its own hold (print 48 hours after delivery; events after the event; stays after check-in; coaching after the session), and a vendor has one balance across their businesses. They withdraw what is available, at least ₹100, with the Cashfree fee taken from the payout; money on hold shows its date but can't be withdrawn, and an admin can release one order early with a reason in the audit log. Payments ends with a Statement from `GET /v1/vendor/payments/statement` (`BusinessService.statement`, `usePaginated`, Show more): each order's share arriving (Pending), becoming available (the same money moving, so no plus sign), and refunds out of it; a line opens the order (`(vendor)/sale/[id]`). The balance card has Withdraw (`BusinessService.withdraw`, `POST /v1/vendor/payouts`): it withdraws everything available after a confirm sheet showing what reaches the account after the fee. The minimum and fee come from `payments.withdrawal`, set by the Ruxstar admin (defaults ₹100 and ₹5.90). Instead of the button the card says why when there is no checked payout method, a withdrawal is on the way, or the balance is under the minimum. A retry after a network error or timeout reuses the idempotency key, so it can't withdraw twice. Payouts show the fee and, when failed, why, with the money back in the balance; the statement adds withdrawals (to the account) and returned withdrawals, which open nothing. Payout notifications (`link.screen: "payments"`) open the Payments tab, and notification links the app doesn't know open nothing instead of breaking the list.
40. **Console payouts (13 Nov 2026, Architecture decision 52):** More → Payouts (`(admin)/payouts`, `payouts.view`) has four tabs. On the way, Failed and Paid list withdrawals (`AdminService.payouts`); a row opens what reaches the bank, the fee, the account, how many times it went to Cashfree, the bank reference or why it failed, and the transfer id. On the way has "Check with Cashfree now" (`checkPayout`, `payouts.manage`), which settles it if Cashfree knows. Held lists delivered orders whose share is still on hold (`heldOrders`), searchable by order number. "Release now" (`releaseHeld`, `payouts.manage`) asks for a reason in a `ReasonSheet`, which goes to the audit log, and the vendor is told it was released early. An order with an open problem can't be released until the problem is settled in Reports. The Modules screen's ledger card edits the withdrawal fee and minimum together (`payoutFee`, `minPayout`; the minimum at least ₹1 more than the fee). Staff get the two new permissions from the server's catalog on the Staff screen.
41. **Coupons (13 Nov 2026, Architecture decision 53):** print orders only. Place order has an Offers section once the order can be priced (`CheckoutCoupons`): a Coupon code box with Apply, and the API's offers best first, each with what it saves or, greyed out, why it doesn't apply yet ("Add ₹50 more to use this."). Applying one re-asks the quote with `couponCode`; the applied coupon shows "You save" with Remove, and a code that can't be used shows the API's reason under the box while the price stays without it. Only a coupon the latest quote accepted is sent when placing. Price lists show "Coupon CODE · Ruxstar offer" (or Shop offer) as a minus line; the shop's Money card adds "Coupon, paid by Ruxstar" back so "You get" adds up. Vendors with a print shop get Coupons on the Dashboard (`(vendor)/coupons`, `CouponService`): New coupon (`(vendor)/coupons/new`) picks the shops it works at, and each coupon card opens to its terms, Change and Switch off. The console has More → Coupons (`(admin)/coupons`, `coupons.view`) with Ruxstar | Vendors and a code search; `coupons.manage` makes Ruxstar coupons (`(admin)/coupons/new`), changes them, and can only switch vendors' coupons off or back on. `NewCouponScreen`, `CouponCard` and `CouponFields` are shared by both: the code and discount are set once; starts and ends are whole days in India time from day chips (a start that has passed can't move); empty limits mean none; and only what changed is sent (`features/coupons/lib/coupons.ts`).
42. **Vendor team (13 Nov 2026, Architecture decision 54):** print shops only; the mocked staff portal and its capability keys are gone. A live business has Team (`(vendor)/businesses/[id]/team`, `TeamService`): Invite (`team/invite`) finds someone by username and picks from the API's ten permissions, where the order ones and earnings tick "See orders" too; up to 20 people, invites included, and an invite lasts 7 days. A member (`team/[memberId]`) shows their status (invited, waiting for identity verification, active), lets the owner change permissions or remove them, and "See what they did". Activity (`businesses/[id]/activity`, owner only) lists what happened at the business in the API's words, with who did it ("You", the member, "A customer" or "Ruxstar"), and a row about an order opens it. Settings → Work (`(customer)/work`, `WorkService`) shows invites with Accept and Decline and the businesses you work at; a place (`work/[id]`) says when verification or a hold stops it, offers Leave, and shows only the areas its permissions allow: Orders (`work/orders/[id]`, `TeamOrderService`, money hidden without "See the shop's earnings"), Shop (`work/shop/[id]`, the vendor's own shop screens through `TeamShopService`, without the GSTIN, publishing or deleting), Coupons (`work/coupons/[id]`, `TeamCouponService`; new ones work at this shop only) and Post as the business (the usual composer with `teamOf`, posted under the owner's name). The console's business screen lists the team, and `businesses.manage` can remove someone with a reason.
43. **Print shop reviews (14 Nov 2026, Architecture decision 55):** a delivered order's tracking screen shows `RateOrderCard` while the order's `reviewUntil` is set (30 days after delivery; null when cancelled, turned down or refunded in full): five stars to tap, then a sheet with an optional note (500 characters). Once written it shows the review with Edit, Delete and until when, or Ruxstar's reason if it was removed. Shop cards show the rating ("4.3 (12)" or "New" before 3 reviews); the shop screen has the rating as a fact and the newest 3 reviews with "See all N reviews" (`(customer)/pod/reviews/[id]`, `ShopReviewsScreen`), where anyone can report a review that isn't theirs (`ReportReviewSheet`). The owner of a live print shop has Reviews on the business screen (`(vendor)/businesses/[id]/reviews`); team members with the new "Reply to reviews" permission have it in Work (`(customer)/work/reviews/[id]`). Both use `ReplyReviewsScreen`: Reply, Edit reply, Take the reply down and Open order; shops can't delete reviews. The console's Reports has a Reviews tab (`ReviewReportsQueue`): Keep it up, or Remove review with a reason the customer is told. The notifications `review.posted`, `review.replied` and `review.removed` open the shop's reviews, the work reviews or the order. Words and limits are in `features/reviews/lib/review.ts`; services are `ReviewService`, `ShopReviewService`, `TeamReviewService` and `ReviewReportService` (`review-service.ts`).
44. **Pay on team invites and the Work button (14 Nov 2026, Architecture decision 56):** Invite and an invited member have `PayFields` (`features/team/components/PayFields.tsx`): an optional amount in rupees, then "Paid per" (month, week, day, hour, order) and a note up to 120 characters. The owner can change it until the person accepts; after that the member screen shows it read only, as what they accepted. `InviteCard` shows the pay large ("₹15,000 a month", `payLine` in `features/team/lib/team.ts`) or "Not mentioned. Ask … before you accept."; Work titles the list "Job offer" or "N job offers" and, with more than one, says to compare them; a place's line starts with its pay. The feed's top bar has a briefcase button before the bell that opens Work, with a badge counting open offers (`useOfferCount`, refreshed on focus). `TeamService.update` replaces `setPermissions` and sends only what changed. Ruxstar only shows the pay; nothing goes through the ledger.
45. **Delivery, phase 1 (14 Nov 2026, Architecture decision 57):** riders work in a separate app, Ruxstar Delivery (`ruxstar-delivery-application-services`), signing in with the same account; the mock `(partner)` area, `features/delivery`, `delivery-service.ts` and `delivery.mocks.ts` are gone. This app keeps four parts of delivery. (1) Verification: Profile has a bicycle button after the storefront button that opens `settings/delivery` (`DeliveryVerificationScreen`). It asks for identity verification first; then the driving licence number and a photo of its front, bike or scooter, the number plate and a photo showing the plate (camera or gallery, 1600 px JPEG, raw bytes to `/v1/kyc/delivery/photos/{licence|vehicle}`), and Send for review. Approval turns the button white, adds the delivery role and says to open Ruxstar Delivery. (2) Checkout: when a shop charges per km, Place order has "Use my location" (`DropLocation`, expo-location, reverse geocoded into empty fields) and sends `address.point`; otherwise the API geocodes the typed address. The quote and price lists show "Delivery · N km". (3) Who delivers: a ready order's shop screen (`DeliverySection`, owner or team with "Move orders") has "Send with a rider": team members with the new "Deliver orders" permission who are verified riders, or a Ruxstar partner with the pay and how many are online in the city. While a trip is live the shop's next steps are hidden (`tripActive`), it shows the rider and can cancel before pickup; a rider's cancel hands the order back. Without a rider the owner marks it delivered as before. (4) The customer's tracking screen shows `RiderCard`: status, name, photo, vehicle, Call, and the 4-digit code to give the rider. Products & delivery has a delivery charge: base, per km and the km the base covers, capped by `catalog.limits.deliveryFee`. The console's Verification has Identity | Delivery partners, with the licence and vehicle and their 10-minute photo links; Modules has "GSTIN needed to publish" on business modules and, on the delivery module, partner pay (default ₹30 for 3 km, then ₹8 a km), the most a shop can charge and how long an offer waits. "A GSTIN" joins what a draft still needs. Delivery notifications open Delivery verification here.
46. **Search (14 Nov 2026, Architecture decision 58):** the Search tab stays people only (name or @username); shops are searched in Discover. Before typing it shows Recent, the last 10 people opened from Search on this device for this account (`useRecentPeople`, AsyncStorage key `ruxstar.search.recent.<userId>`, × on each and Clear), then New on Ruxstar. Discover's box ("Shop, what they print, or a city") sends `q`, which the API matches against the shop name, what it prints (with everyday words such as "visiting cards", "xerox" and "flex") and its city or area; each page lists shops in the customer's profile city first, then open ones. No post search.
47. **Delivery partner withdrawals (14 Nov 2026, Architecture decision 59):** partners add their payout account and withdraw in the Ruxstar Delivery app's Earnings, not here; their account is separate from the one a shop is paid to. Each delivery's pay can be withdrawn 48 hours after it, longer only while a "not received" report is open. The console shows it: Payouts lists partners' withdrawals with vendors', marked Partner in the row (`StaffPayout.payee`), with Check with Cashfree; a held order shows the partner's pay and when they can withdraw it (`HeldOrder.partner`); Modules → Delivery has the partner withdrawal fee and minimum (the same `Withdrawals` fields as the ledger, worded for partners). A `delivery_earnings` notification opens delivery verification.
48. **Help tickets (14 Nov 2026, Architecture decision 60; the delivery app has the same screens, and can tie a ticket to a delivery):** Settings has Help & support (`(customer)/support`): your tickets, latest activity first, with a dot when Ruxstar replied since you looked, and Message support (`support/new`): a topic (Orders & payments, Refunds, Verification, My business, Delivery, Account & sign-in, Safety & reports, App problem, Other), a subject (3 to 80), what happened (2000) and up to 3 photos, sent one by one to the first message after the ticket is made (1600 px JPEG). A ticket (`support/[id]`, `TicketScreen`) is a thread with Ruxstar's replies on the left, a reply box with photos, and "My problem is solved"; it checks for replies every 30 seconds while open. A solved ticket says until when a reply reopens it (7 days), then it is closed and offers "Open a new ticket". "Contact support" places now open a ticket with the topic and what it is about filled in: verification and delivery verification on hold, a business on hold (the owner's links the business), a coupon Ruxstar switched off, the phone number on Edit profile, and "Get help with this order" on a print order for the customer and the shop owner (not team). A login for an account on hold answers `ACCOUNT_ON_HOLD` with a 2-hour support pass: `useAuthRequest` keeps it in memory (`useSupportPassStore`, never stored) and opens `(auth)/hold`, the same screens signed out with the API's general message and Back to log in; the reason stays with the team. `support.replied`, `support.resolved` and `kyc.reopened` notifications open the ticket or verification. The console (`support.view`, `support.manage`) has Help tickets in More and a dashboard tile: a queue (`(admin)/support`) by Open, Waiting on them and Resolved, filtered by Mine or Nobody on it and topic, searchable by ticket number, with overdue and urgent flags and counts; a ticket (`support/[id]`) with who sent it, what it is about and its state, links to the account and business, status, priority, assignee ("Assign to me") and topic that save at once, and Reply (or Send and resolve) or Note for the team. When it is about verification on hold, `kyc.review` has Reopen verification, which gives one more try and tells them. Reply-by times (`support/settings`) default to urgent 2 hours, high 8, normal 24 and low 72, and the team can change them. Words and limits are in `features/support/lib/support.ts`; services are `SupportService` and `SupportDeskService` (`support-service.ts`).
